# 真实工具调用：查询库状态与检索文献

## 为什么从这个例子开始

现有 RAG 是我们写好的固定流程：收到问题后，程序按设置检索、重排，再让 DeepSeek 回答。这次增加一个不同点：**模型先提出“我要调用哪个工具”，程序再执行。**

例如问“文献库有几篇、多少页”：DeepSeek 没有访问你电脑内存的能力，训练知识也不包含当前索引状态，所以需要一个能读取实际状态的工具。我们已经有 `GET /index/status`，直接复用它，不再安装框架、下载模型或改网页。

这是独立的 `tool_calling_demo.py`，不改变原有 `/ask`。它使用 DeepSeek 的 Chat Completions 工具调用接口；现有 RAG 的 Responses 调用保留不动。

第一阶段已由用户实际运行：模型请求 `get_library_status({})`，Python 返回 1 篇文献、16 页已索引 PDF、79 个切片，模型据此回答。第二阶段在同一脚本增加文献检索工具，学习模型如何在两个工具之间选择，以及如何填写参数。

## 为什么增加检索工具，而不是再写一套 RAG

用户问“库里有多少篇”时，状态工具就足够；问“构建 MJO 指数用了哪些变量”时，数量没有帮助，需要查原文。因此同时提供两个工具，并在说明中区分用途：

| 工具 | 模型填写的参数 | 本地程序实际调用 |
| --- | --- | --- |
| get_library_status | `{}` | `GET /index/status`，返回三个数量 |
| search_documents | `{"query": "构建 MJO 指数使用了哪些变量？"}` | `POST /search`，返回原文与引用信息 |

工具名不是 HTTP 地址。模型根据声明提出工具名和参数；Python 只执行白名单中的工具，将其对应到固定的本地接口，不允许模型指定任意 URL 或执行任意代码。程序中没有根据“是否包含 MJO”之类的关键词替模型选工具。

检索复用已跑通的 E5＋Cross-Encoder，保持 `candidate_k=10`、`top_k=3`。这两个参数由程序固定，不让模型自行调整，先把学习重点放在选工具和填写 `query` 上。`/search` 只检索，不调用生成模型；不能在这里使用 `/ask`，否则工具内部又生成一次答案，再交给外层模型，增加重复请求。

## 工具说明与真实函数为什么要分开

给模型的是工具的“使用说明”，不是 Python 源码：

- `name`：工具名，本例为 `get_library_status` 或 `search_documents`。
- `description`：什么时候应该用它，以及它能做什么。
- `parameters`：参数的 JSON Schema。`type: object` 表示参数是 JSON 对象；状态工具的 `properties` 为空，调用时传 `{}`。检索工具在 `properties` 中声明 `query` 是字符串，`required: ["query"]` 表示它必填。`additionalProperties: false` 表示不接受额外字段。

真正的 `get_library_status()` 则留在本地 Python 中。它读取本地 API，只挑出文献数、已索引 PDF 页数和切片数，不把本机文件路径、快照路径或 API 密钥发给模型。这里的 PDF 页数是已索引的页数，不能一概当成原 PDF 的总页数。

`search_documents(query)` 同样在本地执行。Python 将模型给出的 `query` 放进 `/search` 请求的 `question` 字段，再将检索结果中的 `rank`、文件名、页码、切片编号和原文交回模型；不发送本机完整路径、向量或整个索引。这里的 `query` 是模型要填写的工具参数，不是第二次由你手动输入的问题。

**工具说明不是执行权限。** 即使模型输出了一个名字，程序仍会检查它是否是允许的工具，并验证参数；不是把模型生成的任意文字当代码执行。

声明中的参数要求也不能代替本地验证：Python 仍会拒绝未知工具、多余字段、缺少的 `query` 及不符合长度要求的检索文本。文献原文被当作依据，不作为指挥程序的新指令。

## 两次请求怎样连起来

第一次把问题和工具说明发给模型。模型若判断需要状态，就返回类似这样的调用请求，而不是自己去访问 HTTP 接口：

```text
get_library_status({})
```

程序收到这个请求，执行真实的本地函数，取到当前数量。随后把**模型提出的调用和程序取得的结果一起保留在消息记录里**，再发给模型。第二次模型才有实际数据，可以用自然语言回答。

换成论文问题时，相同机制对应 `search_documents({"query": "构建 MJO 指数使用了哪些变量？"})`：回传的是检索依据，第二次模型根据这些原文回答并引用来源。不是先查数量、再固定查原文；模型可以在第一轮选择适合的工具。同时提出两类问题时，也可以在同一轮请求两个工具，程序分别执行并逐一回传结果。

消息中的三个角色承担不同职责：

| role | 这个例子中代表什么 |
| --- | --- |
| user | 你提出的库状态或论文问题 |
| assistant | 模型提出工具调用，或给出最终回答 |
| tool | Python 执行工具后返回的实际数据或错误 |

`tool_call_id` 是调用与结果的对应编号：模型提出一次调用时附上 ID，程序回传结果时原样带回，模型才能知道这份结果回答了哪次请求。

第一次 `tool_choice="auto"`，允许模型选择工具或直接回答；如果模型没有提出调用，脚本会如实打印“没有查询库状态或检索文献”，不会伪造成功。第二次 `tool_choice="none"`，只让模型组织最终答案，因此本例最多两次模型请求，不构造无限循环。

本例显式关闭思考模式，先学会普通工具消息的往返。思考模式下的工具调用还需要保留、回传推理内容，本阶段不引入这层复杂度。

## 由你运行

保持现有 FastAPI 服务运行。若尚未启动，在项目虚拟环境中运行：

```powershell
python -m uvicorn api:api --reload --host 127.0.0.1 --port 8000
```

在 VS Code **另开一个终端**，进入 `simple-document-qa` 并确认已激活同一个 `.venv`，然后运行：

```powershell
python tool_calling_demo.py
```

不要先停止服务：脚本要通过正在运行的服务读取状态或检索索引。沿用现有 `.env` 和依赖，无需安装新库。正常调用工具后共发送两次真实 DeepSeek 请求，会产生费用。状态工具不运行本地模型；文献检索工具会运行本地 E5 和重排模型，但不在工具内部调用 DeepSeek。两者都不修改索引。

也可以自己换问题：

```powershell
python tool_calling_demo.py "帮我看看现在文献库一共有多少个文本切片。"
```

观察输出中“模型请求工具 → Python 返回实际数据 → 模型根据数据回答”的联系。数量取自当前服务，没有在脚本里写死；若服务未运行，工具返回错误，模型应解释查询失败，不能凭记忆报数量。

第一阶段状态查询已经成功，不用为了本次练习重复运行。现在在同一个第二终端运行一次文献问题：

```powershell
python tool_calling_demo.py "请根据文献回答：构建 MJO 指数使用了哪些变量？请引用 PDF 页码。"
```

重点看 `[2]` 中实际工具名是否为 `search_documents`、参数是否含 `query`，以及 `[3]` 中的原文能否支撑最终回答。不要把这里写出的调用示例当作实际运行记录。

已有持久化 E5 索引和模型缓存时，无需重新加载文献或建立索引。服务重启后首次检索可能需要加载两个模型，脚本为该本地请求设置 180 秒等待上限；这不是固定耗时，也不是模型会连续生成 180 秒。缺少 E5 索引或本地模型缓存时，工具报告失败，不自动下载或切换检索方式。虽然检索使用 HTTP POST，请求的业务操作仍只是读取与检索，并不修改资料库。

## 与 Agent 的关系

这个例子演示了工具选择、参数生成和结果回传，但不必把它称为复杂 Agent。它只有两个只读工具、一次工具执行阶段和最多两次模型请求。模型选择工具不等于拥有无限自主权限；更完整的 Agent 通常还允许模型根据结果继续选择工具、推进多步任务，并需要明确的停止条件和权限边界。本阶段先学会选工具，不增加自主循环。

实现依据：[DeepSeek 官方 Tool Calls 示例](https://api-docs.deepseek.com/guides/tool_calls/)、[Chat Completions 参数](https://api-docs.deepseek.com/api/create-chat-completion/)。
