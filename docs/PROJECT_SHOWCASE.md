# 科研文献 RAG 问答助手：演示与项目讲解

## 1. 项目定位

面向科研论文阅读的本地文献问答应用：导入 PDF，使用中文问题检索英文原文，再由 DeepSeek 根据选中的片段组织答案，同时展示出处、PDF 页码和原文。

技术栈：Python、FastAPI、Sentence Transformers、multilingual-e5-small、Cross-Encoder、DeepSeek API（支持官网及阿里云百炼接入）、HTML / CSS / JavaScript。

项目特色不是重新训练语言模型，而是把文献处理、两阶段检索、模型调用、持久化和网页展示连成一个可操作的应用。

## 2. 三分钟演示

### 准备

在已激活项目虚拟环境的终端启动：

```powershell
python -m uvicorn api:api --reload --host 127.0.0.1 --port 8000
```

打开 http://127.0.0.1:8000/ 。已有论文和 E5 索引时，不需要重新加载或重新建立索引。若是全新环境，先按照 README 安装依赖、配置本地 .env、准备模型缓存并加载文献。

首次请求需要加载本地模型，可以先点击“只检索”完成本地模型加载；它不调用 DeepSeek。点击“生成答案”才会发送问题与选中片段，并产生真实 API 用量。录屏或共享屏幕前，收起包含密钥的文件。

### 第一步：展示资料与处理结果

指向左侧文献库，说明：

> 这里不是模型自带的知识，而是我导入的论文。页面显示当前文献数量、PDF 页数和切片数，索引保存到本机，重启服务后可以恢复。

现有 MJO 演示库为 1 篇论文、16 页、79 个切片。页面从接口读取这些数值，不是前端写死的数据。

### 第二步：说明两阶段检索

保留 E5 检索、启用重排、候选数量 10、最终片段数 3，点击示例问题：

> 构建 MJO 指数使用了哪些变量？

说明：

> E5 先从文献库中选取十个候选，再由 Cross-Encoder 对问题和候选逐对打分，最后只保留三段作为回答依据。

### 第三步：展示答案和引用

点击“生成答案”，等待真实返回，再展开 PDF 第 1 页、切片 1 的原文。

说明：

> 答案列出了 850 hPa 纬向风、200 hPa 纬向风和 OLR。这里可以直接对照论文摘要，看到具体依据。后端还返回了该片段在 E5 中的原名次和重排后的名次。

已记录的实际示例中，该片段原排名为 7，重排后为 3；完整中文问答已经由用户运行成功。

### 第四步：收束技术路线

> 前端负责提交问题和显示结果，FastAPI 接收请求；公共业务函数组织检索、重排和生成。索引在本地持久化，E5 和重排模型在本机运行，选中的文字片段才交给 DeepSeek 生成答案。

无需为了演示再次替换资料库、反复测试同一问题或打开所有代码文件。

## 5. 面试讲解提纲

### 为什么不直接调用大模型？

模型不会自动知道本机 PDF 的内容。RAG 先检索资料，把相关原文作为当前请求的上下文，再让模型回答。原文与页码也能帮助使用者核对依据。

### E5 和 DeepSeek 有什么不同？

E5 输出用于检索的向量；DeepSeek 输出自然语言答案。Cross-Encoder 则对“问题、片段”文本对输出相关性分数，负责重排。这是三个不同的职责，不是让一个模型做三次相同的工作。

### 为什么切片需要重叠和页码？

片段长度影响信息完整性和上下文大小，重叠能保留边界附近的内容；页码和字符位置用于定位来源。当前按页、固定字符数切片，实施简单，也便于返回引用。PDF 版面复杂时还可以进一步改进解析，但当前项目不依赖额外 OCR 或表格解析。

### 为什么召回 10 段，却只给生成模型 3 段？

召回阶段先保留较宽的候选范围，降低关键依据因名次靠后被过早舍弃的情况；重排后选少量片段，控制发给生成模型的文本量。10 和 3 沿用实际跑通的演示设置，两个参数分别控制不同阶段。

### 两次排序是否重复？

E5 分别编码问题和片段，使用余弦相似度筛选；Cross-Encoder 将问题与候选联合输入，直接对这一对文本打分。前者负责从资料中找候选，后者花额外计算在少量候选中精细选择。

### 为什么使用 JSON 保存索引？

本项目在本机、单服务进程运行，当前文献规模小。JSON 可以保存现有字典与列表结构，不增加数据库依赖，也方便查看内容。运行时从快照恢复到内存执行检索；硬盘保存和内存计算是不同职责。当前没有使用专门的向量数据库。

### 怎么判断是检索问题，还是模型生成问题？

通过 /search 单独查看选中的原文：如果其中没有完整依据，先排查检索和片段选取；如果有依据但答案不对，再排查 Prompt 和生成。/search 与 /ask 复用同一套检索、重排函数，减少两处行为不一致的问题。

### 一个具体的排错案例如何讲？

按“现象 → 定位 → 改动 → 结果”讲：

1. 现象：问 MJO 指数的输入变量，论文中有答案，初始选中片段却无法完整回答。
2. 定位：用独立检索接口看原文，确认不是 PDF 完全没提取出来，而是关键片段排名靠后。
3. 改动：加入 E5 语义检索，再将候选数量和最终数量分开，引入重排。
4. 结果：中文示例中，关键依据从 E5 第 7 名升至重排第 3 名，DeepSeek 返回了三个变量并引用第 1 页原文。

如果补充英文对照，可说明同一英文问题下该片段从 TF-IDF 第 32 名升到 E5 第 4 名。英文对照和中文重排是两组不同条件，不混算成同一个提升百分比。

### 前端和后端怎样配合？

浏览器里的 JavaScript 将问题和参数组织成 JSON，通过 fetch 调用同源 /ask 或 /search；后端完成处理后返回 JSON，前端再展示答案和引用。密钥保留在后端，页面不需要接触它。页面本身不负责模型推理。

### 这个项目现在算 Agent 吗？

主应用是固定 RAG 工作流：程序预先规定检索、重排和生成的顺序。独立的 `tool_calling_demo.py` 已实际演示由模型选择 `get_library_status` 或 `search_documents` 并填写参数，Python 校验、执行工具，再将结果交回模型。这个示例限制一次工具执行阶段、最多两次模型请求；主应用与独立工具示例分别讲述，已经跑通的能力包括工具选择与结果回传。
